# 03. 실제로 돌린 실험·테스트와 실패 지점

## 3.1 무엇을 실험했나 (도그푸딩)

오케스트레이션의 성능을 재려고 **director에게 director 자신을 고치게** 했다(도그푸딩):
목표 = "이 저장소에 **IDA Pro MCP를 쓰는 analysis 모드**를 새로 추가하라"
(요구: `analyze` 서브커맨드, `--allowedTools`로 IDA MCP 허용하는 ANALYST 어댑터, Finding 스키마(pydantic), 설계 문서. 기존 코드는 수정 금지, 새 파일로만.)

이 목표를 quick/standard 프로파일로 **여러 번** 돌렸다.

## 3.2 결과: "실패율이 높아 보였다" — 근데 원인을 해부하면

실패는 **세 겹**이었고, 대부분 AI의 코드 품질 문제가 **아니었다.**

### (A) 내 환경 실수 — AI 잘못 아님
| 증상 | 원인 | 교훈 |
|---|---|---|
| `pytest`가 테스트 0개로 중단(exit 2) | director 자체 테스트가 `requests`를 import하는데 **의존성 미설치** → 수집 단계에서 전체 중단 | 검증 러너의 의존성은 **requirements 전체**를 깔아야. 일부만 깔면 "0 passed"로 거짓 실패 |
| config.toml/yaml/json 파싱 깨짐 | PowerShell `Set-Content -Encoding UTF8`이 **UTF-8 BOM을 붙임** → TOML/YAML/JSON 파서가 거부 | Windows에서 설정 파일은 **BOM 없이** 써야(파이썬/전용 에디터로). `sed`로 바이트 단위 제거 |
| `[projects.'...한글경로...']` unclosed table | config.toml에 **모지바케(깨진 한글 경로)** 블록 | 경로에 한글/특수문자가 섞이면 TOML 테이블 키가 깨짐 |

→ 이 층은 전부 **"포장"의 문제**였다. AI가 짠 코드와 무관하게, 내가 환경을 덜 갖춰서 검증이 거짓 실패했다.

### (B) 검증 게이트의 과한 판정 — 구조는 맞는데 설정이 과함
- 실시간 관전(`watch_live.py`)으로 잡아낸 진실: 어떤 런은 **테스트 123개 통과 / 1개 실패**, **리뷰어는 pass**, 그런데 **최종 FAIL**.
- 그 1개 실패 = `tests/test_v300i_failure_learning_loop.py` — **analysis 모드와 무관한, director 자체의 기존에 깨진 테스트**.
- 원인(코드): `core/orchestrator.py`의 `builds_on_director_work` 가드가 켜지면 `only_preexisting_failures()`(기존 실패 관용)가 **통째로 꺼진다.** 우리 런은 worktree를 **이어받기(continuation)** 라 그 플래그가 켜져서, 무관한 기존 실패 1개로 전체가 FAIL.
→ "AI가 멍청해서 실패"가 아니라 **게이트가 사전 실패를 같이 세서** 떨어뜨린 것.

### (C) 진짜 구조적 한계 — 아래 04에서 상술
- Builder(claude)가 **멀티파일 결과를 통짜 JSON으로 반환**하다 큰 출력에서 **제어문자로 JSON이 깨짐**(`Invalid control character at line 1 column 11155`) → **codex로 failover**. "코드 짜다 갑자기 codex가 짜는" 현상의 정체.
- 역할 호출이 **매번 1회성(세션 미연속)** → 매 스텝 콜드스타트.

## 3.3 증거: AI 코드 자체는 멀쩡했다

- 생성된 analysis 모드(ANALYST 어댑터, Finding 스키마, CLI, 문서, 테스트)는 **`requests` 설치 후 56개 테스트 전부 통과**.
- 리뷰어 판정도 **pass(P1 0 / P2 0)**.
- 즉 "실패율 높음"의 체감은 **대부분 (A)+(B) 때문**이었고, (C)만이 진짜 도구 한계였다.

## 3.4 "HEAD는 왜 실패 시 재시도 안 하고 멈췄나"
- 미션은 **단계 예산(quick=2단계)** 안에서만 돈다. 2단계를 다 쓰면 `미션 중단 - 단계 예산 소진`.
- HEAD가 "멈춘" 게 아니라 **예산을 다 쓴** 것. standard(6)로 올리면 더 간다. 이건 버그가 아니라 설계된 무한루프 방지 장치(01-1.3).

## 3.5 핵심 교훈
> **오케스트레이션의 "실패"를 볼 때는 세 층을 분리해야 한다 — ① 내 환경/포장 문제, ② 게이트/설정의 과함, ③ 진짜 구조 한계.**
> 로그를 안 보면 셋이 뭉뚱그려져 "AI가 멍청하다"로 오해한다. 그래서 **실시간 관전 + 사람이 읽는 리포트**(04의 도구)가 필요했다.
