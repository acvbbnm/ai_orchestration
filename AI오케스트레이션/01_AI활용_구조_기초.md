# 01. AI 활용 구조의 기초 — 오케스트레이션은 왜 나오는가

## 1.1 다섯 가지 "엔지니어링" 층위

AI를 "잘 쓴다"는 건 모델을 바꾸는 게 아니라 **모델을 둘러싼 구조**를 설계하는 일이다. 층위별로:

| 층위 | 무엇을 설계하나 | 예 |
|---|---|---|
| **프롬프트 엔지니어링** | 한 번의 질문/지시를 어떻게 쓰나 | 역할 부여, 출력 형식 지정, few-shot |
| **컨텍스트 엔지니어링** | 모델이 **무엇을 보게** 할 것인가 | 어떤 파일/기록/결정을 주입하고 무엇을 생략할지, 토큰 예산 관리 |
| **하네스(harness)** | 모델을 **어떻게 구동**하나 | CLI 플래그, 도구 권한(allowedTools), 샌드박스, 출력 파싱 |
| **루프(loop)** | 실패/미완을 **어떻게 반복**하나 | 검증→수정→재검증, 재시도 횟수, 중단 조건 |
| **그래프(graph)** | 여러 역할/단계를 **어떻게 연결**하나 | 설계→구현→검수→판정의 상태 전이 |

> 핵심 통찰: **모델이 올라갈수록 "코딩 실력"보다 "사고·문제해결·계획 능력"이 좋아진다.** 그래서 강한 모델은 **HEAD(설계·판정)** 에, 코딩 잘하는 모델은 **BUILDER** 에 배치하는 게 합리적이다.

## 1.2 왜 단일 에이전트로는 부족한가 → 오케스트레이션의 등장

프로그램 하나를 AI로 개발한다고 하자. 한 모델에게 전부 시키면:

1. **컨텍스트가 터진다** — 요구사항 + 전체 코드 + 테스트 + 수정 이력을 한 창에 다 넣으면 토큰 한계를 넘고, 넘지 않아도 "주의가 흐려진다".
2. **자기 검증의 맹점** — 같은 모델이 짜고 같은 모델이 "맞다"고 하면 확증편향이 생긴다. **독립된 검수자**가 필요하다.
3. **단계별 통제 불가** — 어디서 틀렸는지, 어디까지 됐는지 추적이 안 된다.

그래서 **역할을 나눈다**:

```
        ┌──────────────────── 루프(수정 반복) ───────────────────┐
        ↓                                                        │
 [HEAD] 설계·지시 ──order──▶ [BUILDER] 구현 ──files──▶ [검증] 테스트
   ▲                                                        │
   │                                                        ▼
   └──판정(PASS/FAIL)◀── [REVIEWER] 독립 검수 ◀──diff────────┘
        │
        └─(완료 시)─▶ [MENTOR] 학습 브리핑 → 사람
```

이게 **오케스트레이션**이다. "AI 사무실"이라 불리는 것(ChatDev, MetaGPT)도 같은 발상 — 에이전트에게 **역할(PM/설계자/엔지니어/검수자)** 을 주고 **산출물을 주고받게** 한다.

## 1.3 사람의 개입과 무한루프 방지

자동으로 돌리면 "고치다 또 틀리고 또 고치는" 무한루프에 빠질 수 있다. 그래서 오케스트레이터는:
- **예산(budget)**: 단계 수(max_steps), 수정 횟수(max_repairs), 연속 실패 한도.
- **중단 조건**: 예산 소진, 계획 불가, 사람 승인 필요(돈·실제 계정·되돌릴 수 없는 행동).
- **프로파일**: 작업 크기별 예산 묶음(quick/standard/deep).

사람은 **목표를 주고, 중단점에서 판단**하는 자리에 선다. (이게 "AI는 탑다운으로 개발하고, 나는 바텀업으로 학습한다"의 구조적 근거 — 개발 자동화와 **학습**은 분리되므로 MENTOR 역할을 따로 둔다.)

## 1.4 "구독 CLI로 돌린다"는 제약의 의미

대부분의 오케스트레이션 프레임워크(LangGraph/CrewAI/AutoGen)는 **모델 API를 호출**한다 = 토큰당 과금. 반면 GPT/Claude/Gemini **구독**을 쓰면:
- 공식 CLI(Claude Code / Codex / Gemini)의 로그인 세션으로 호출 → 구독에 포함, 추가 과금 없음.
- 대신 프레임워크가 "대화 상태"를 직접 못 쥔다 — **CLI가 세션을 쥐고 있어야** 맥락이 이어진다.

이 제약이 뒤에서(03~05) 핵심 쟁점이 된다. `ai-dev-director`는 "구독 CLI만 쓴다"를 선택했는데, 바로 그 선택이 **세션 연속성 문제**를 낳는다.
